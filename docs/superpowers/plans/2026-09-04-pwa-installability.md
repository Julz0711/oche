# PWA Installability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Oche installable as a PWA (Android/Chrome "Add to Home Screen", iOS Safari "Add to Home Screen") with an on-brand icon set, with zero caching/offline logic.

**Architecture:** A generated web app manifest (`app/manifest.ts`) and iOS meta tags reference a small set of on-brand icon PNGs, generated once via a one-off script using `next/og`'s `ImageResponse` (already ships with Next.js — no new dependency). A minimal no-op service worker satisfies Android/Chrome's installability heuristics without doing any caching.

**Tech Stack:** Next.js 16 App Router file conventions (`manifest.ts`, `icon.png`, `apple-icon.png`), `next/og`'s `ImageResponse` (Satori-based JSX-to-PNG renderer, used standalone in a Node script — verified working in this exact environment before writing this plan).

**Spec:** [docs/superpowers/specs/2026-09-04-pwa-installability-design.md](../specs/2026-09-04-pwa-installability-design.md)

## Global Constraints

- No caching, fetch interception, or offline fallback logic anywhere in the service worker — that's a separate, later sub-project.
- No custom install-prompt UI — rely on the browser's native install affordance.
- Icons use only the app's existing 3 relevant design tokens: `--oche` (`#141A18`), `--wire` (`#C0A15C`), `--chalk` (`#F2F4F3`) — no new colors.
- `app/manifest.ts`'s `background_color`/`theme_color` import `tokens` from `@/lib/theme` directly rather than hardcoding hex a second time (a DRY improvement over the spec's literal suggestion, made during planning — see Task 2).
- **Deviation from the spec's literal text, decided during planning:** the spec says to replace `app/favicon.ico` with a real multi-resolution `.ico` file. No ICO-encoding tool is available in this environment (no ImageMagick, no `sharp`, confirmed absent). Next.js's file-based `icon` convention supports `.png` directly and is fully equivalent for this purpose (`app/icon.png` → Next.js auto-generates the correct `<link rel="icon">` tag) — so this plan deletes `app/favicon.ico` and adds `app/icon.png` instead, achieving the spec's actual goal (replace the stock Next.js icon with an on-brand one) without needing ICO tooling this environment doesn't have.
- No automated tests for this feature — there is no meaningful logic to unit test (static config, static assets, a no-op service worker). Verification throughout is manual, per the spec's own Testing section.

**Interfaces:**

- [ ] **Step 1: Write the icon-generation script**

Create `scripts/generate-pwa-icons.js`:

```js
// scripts/generate-pwa-icons.js
// One-off script: renders the on-brand dartboard/target icon via next/og's ImageResponse (a
// Satori-based JSX-to-PNG renderer that ships with Next.js — no extra dependency needed) at each
// required PWA icon size, and writes the resulting PNGs directly into the repo.
// Run with: node scripts/generate-pwa-icons.js

const { ImageResponse } = require('next/og');
const React = require('react');
const fs = require('fs');
const path = require('path');

const OCHE = '#141A18';
const WIRE = '#C0A15C';
const CHALK = '#F2F4F3';

/** Concentric-ring dartboard/target motif. `padding` insets the whole design from the canvas
 *  edge — used for the maskable variant, which the OS crops to a circle/rounded-square, so
 *  content must stay within the inner ~80% "safe zone" (a 10% padding on each side). */
function targetIcon(size, padding) {
  const inner = size - padding * 2;
  const ring = (scale, color, child) =>
    React.createElement(
      'div',
      {
        style: {
          width: inner * scale,
          height: inner * scale,
          borderRadius: '50%',
          background: color,
          display: 'flex',
          alignItems: 'center',
          justifyContent: 'center',
        },
      },
      child
    );

  return React.createElement(
    'div',
    {
      style: {
        width: size,
        height: size,
        background: OCHE,
        display: 'flex',
        alignItems: 'center',
        justifyContent: 'center',
      },
    },
    ring(1, WIRE, ring(0.66, OCHE, ring(0.4, WIRE, ring(0.18, CHALK))))
  );
}

async function renderIcon(size, padding, outPath) {
  const res = new ImageResponse(targetIcon(size, padding), { width: size, height: size });
  const buf = Buffer.from(await res.arrayBuffer());
  fs.mkdirSync(path.dirname(outPath), { recursive: true });
  fs.writeFileSync(outPath, buf);
  console.log(`wrote ${outPath} (${buf.length} bytes)`);
}

async function main() {
  await renderIcon(192, 0, path.join(__dirname, '..', 'public', 'icon-192.png'));
  await renderIcon(512, 0, path.join(__dirname, '..', 'public', 'icon-512.png'));
  await renderIcon(512, Math.round(512 * 0.1), path.join(__dirname, '..', 'public', 'icon-maskable-512.png'));
  await renderIcon(180, 0, path.join(__dirname, '..', 'app', 'apple-icon.png'));
  // app/icon.png reuses the same 192px render as public/icon-192.png — Next.js's file-based
  // `icon` convention picks this up for the browser-tab icon, replacing the stock favicon.ico.
  fs.copyFileSync(
    path.join(__dirname, '..', 'public', 'icon-192.png'),
    path.join(__dirname, '..', 'app', 'icon.png')
  );
  console.log('wrote app/icon.png (copied from public/icon-192.png)');
}

main().catch((err) => {
  console.error(err);
  process.exit(1);
});
```

### Task 3: No-op service worker and registration

**Files:**
- Create: `public/sw.js`
- Create: `components/PwaRegistration.tsx`
- Modify: `app/layout.tsx`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: nothing consumed by other tasks — this task is self-contained.

- [ ] **Step 1: Write the no-op service worker**

Create `public/sw.js`:

```js
// public/sw.js
// A minimal, intentionally no-op service worker. Its only job is to exist and be registered —
// Android/Chrome's installability heuristics look for an active service worker even when there's
// nothing to cache. It does not intercept fetches or cache anything; that's a separate, later
// "Offline" sub-project's job, which needs its own design given this app's real-time,
// server-authoritative architecture (match state is never meaningfully available offline the way
// a static page would be).
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (event) => event.waitUntil(self.clients.claim()));
```

- [ ] **Step 2: Write the registration component**

Create `components/PwaRegistration.tsx`. This lives directly under `components/`, not in `atoms/molecules/organisms`, because it renders nothing — it's a side-effect-only component (registers a browser API on mount), which doesn't fit those folders' visual-hierarchy purpose:

```tsx
// components/PwaRegistration.tsx
'use client';
import { useEffect } from 'react';

/** Registers the no-op service worker (public/sw.js) on mount. Renders nothing — this is a
 *  side-effect-only component, not a visual one, which is why it doesn't live under
 *  atoms/molecules/organisms alongside this project's UI components. */
export function PwaRegistration() {
  useEffect(() => {
    if ('serviceWorker' in navigator) {
      navigator.serviceWorker.register('/sw.js').catch((err) => {
        console.error('Service worker registration failed:', err);
      });
    }
  }, []);

  return null;
}
```

- [ ] **Step 3: Mount it in the root layout**

Read `app/layout.tsx` in full again (Task 2 already modified it once). Add the import:

```tsx
import { PwaRegistration } from '@/components/PwaRegistration';
```

Then render `<PwaRegistration />` inside the `<body>`, alongside the existing `<SessionProvider>` — for example:

```tsx
      <body className="min-h-full flex flex-col">
        <PwaRegistration />
        <SessionProvider>{children}</SessionProvider>
      </body>
```

- [ ] **Step 4: Typecheck**

Run: `npx tsc --noEmit`
Expected: clean.

- [ ] **Step 5: Manually verify the service worker registers**

Run `npm run dev`, open the app in a browser, open DevTools → Application → Service Workers. Confirm a service worker for `/sw.js` shows status "activated and is running" with no errors, and confirm the browser console shows no "Service worker registration failed" message.
